# Fixed derivative campaign dispatcher: implementation review note

This is source preparation only. No campaign plan, first-shard audit, receipt, target evaluation, or campaign launch is supplied by this change. The first actual final-domain shard must finish and receive a separate independent audit before the Git owner freezes the campaign card. The dispatcher never treats completed derivatives as a mathematical orbit certificate.

## Fixed scope and admission

`derivative_campaign.py` dispatches exactly the 111 remaining canonical assignments after one explicitly pinned successful shard, in phase/start-column order. There are eight phases and fourteen 64-column blocks per phase (896 coordinates). It invokes the existing, unchanged `launch.py` and `derivative_shard.py`. Every committed shard plan must use precisely the same definition, map, backend, evaluator source bundle, 1024-bit prefix/cache, 1024-bit arithmetic, token chunk, and CPU/resource envelope as the first shard. This dispatcher does not evaluate models or inspect derivative entries. Whole inventories and compact status/input metadata are verified; mathematical derivative auditing remains a separate obligation.

The eventual campaign JSON must have schema `codex-fixed-derivative-campaign-v1`, status `reviewed_measured`, and the exact fields enforced by `validate`. It supplies `execution_checkout`, `sources`, `common`, `first`, `assignments`, and `resources`. Every row has a unique new attempt and a committed plan basename/hash. Exactly 111 canonical rows are required; existing outputs, omissions, duplicates, and changed domains refuse admission. `first` additionally pins an external audit file with schema `codex-first-final-shard-measured-audit-v1`, its author/source, literal first receipt/plan/assignment and map identities, and exact measured elapsed time/RSS. That audit is an explicitly external authority, not a conclusion inferred from a flag by this dispatcher. Root must adapt or produce this compact index from the real independently reviewed first result.

The plan pins a **separate task-owned frozen execution checkout**. The Git owner creates and prepares that checkout, commits the complete dispatcher/source/112 plans/campaign card, privately pushes, and supplies the actual source commit and campaign SHA at invocation. The active research checkout remains available for checkpointing. Startup checks exact tracked bytes, clean HEAD, and ancestry in remotely advertised `origin/main`; missing local remote objects refuse admission and require the Git owner to synchronize. Before every launch and after completion, HEAD/clean status/campaign bytes are rechecked. The dispatcher does no Git mutation. Each existing launcher performs its own reviewed source snapshot and remote admission.

## Measured finite resources

Root chooses actual concurrency only after the first measurement. The card specifies concurrency 1–10 and total CPU reservation at least concurrency+2 and at most 12; workers run one numerical thread. The extra reservation covers the dispatcher and one launcher registration/Git operation. Registrations are serialized: another launcher is not spawned until the prior worker has a validated ownership registration. Existing workers can overlap. Their receipt finalization may overlap and is included in sampled aggregate RSS.

Each existing launcher uses exactly CPU1, nice10, 18 GiB per-worker address-space limit and 3600 seconds. Because unchanged `launch.py` adds ten nice units in its worker pre-exec path, the dispatcher requires a nice0 control-plane parent; launching the dispatcher itself at nice10 would produce the wrong worker priority and is refused. The controller uses a 1 GiB soft AS limit, with 18 GiB inherited hard limit so workers can establish their unchanged envelope. Thread environment variables are set to one and GPU visibility is disabled. This is not CPU-affinity/cgroup enforcement.

The frozen card chooses three explicit integer rational headroom factors, each `factor_milli/1000` in [1,4], from the measured first shard: time, RSS, and storage. No factor is silently fixed to 2. Per-shard predicted time must fit 3600 seconds; the whole forecast charges every batch, every registration allowance and receipt grace. Aggregate RSS and raw-byte forecasts include explicit controller/output reserves. The prototype's 1811-second timing is covered only by a synthetic control demonstrating that a reviewed 1.2 factor can fit where 2 cannot; it is **not** a measurement or admission for this campaign.

Runtime checks before every spawn and on every loop enforce the finite overall deadline, sampled aggregate RSS, minimum MemAvailable, raw-byte watchdog and minimum free disk. RSS is explicitly a sampled watchdog, **not a hard memory cap**. Transient overshoot between samples remains possible. The unchanged launcher supplies each worker's real AS cap and timeout. Completed or failed attempts are retained; no retry, domain change, success selection or automatic continuation is implemented.

## Ownership and termination

Immediately after `Popen`, its handle/PID/expected command are retained in the child table before any fallible `/proc` or pidfd registration. A normal registration validates the launcher birth identity, direct worker parentage, worker birth time/UID/session/group, exact archived command, nice10 and actual 18 GiB AS limits. Parent and worker identities are durably recorded. Linux `/proc` and pidfds are required. Signals use verified pidfds for members of the owned session/group, never broad process names or numeric `pkill`. A leader's exit does not hide live descendants in its still-owned session/group.

On failure, signal, deadline or resource breach, future dispatch stops. A bounded registration grace permits an existing launcher to record its worker. If the manifest is still missing, only the verified launcher is temporarily stopped; a bounded handoff permits a just-forked child to exec, after which the exact command and birth/parent/session identity can recover the worker **for cancellation only**. The launcher is resumed in a `finally`, including STOP-confirmation timeout. A confirmed stopped parent with no worker can have its own registration session terminated. Unknown children are not treated as absence.

Known workers receive TERM, then KILL if still present after ten seconds. The launcher is kept alive to collect its worker exit and immutable attempt receipt. Cleanup errors for one child do not skip its peers. The dispatcher then waits the frozen receipt allowance and verifies actual worker/group termination. Failure-log write errors also trigger cleanup rather than bypassing it.

The existing launcher has an unavoidable fork-before-manifest window. If it dies there before the worker identity was established, this implementation reports **uncertain ownership**, stops the campaign, retains the observed evidence and does not guess at orphan ownership or claim termination. Likewise unresolved PID identity, lingering receipt writer, surviving group, or failed ownership inspection leaves a distinct unsealed `finalization-pending.json`; no success or immutable closed-attempt claim is made. This is a remaining operational limitation of the unchanged launcher, not a fabricated successful cleanup. Root must resolve any such occurrence before further work. SIGKILL of the dispatcher itself or host failure cannot run Python cleanup and needs external ownership recovery; the dispatcher makes no contrary guarantee.

## Validation and current release boundary

Twenty-eight controls pass in 6.42 seconds using CPU/thread1, nice10, no model, checkpoint, target artifact, Git network or Git mutation. Synthetic plans contain all 112 canonical assignments. Tiny real subprocess controls cover overlapping workers with sequential registration, complete failure/receipt preservation, low-memory and deadline cancellation, SIGTERM, unregistered-worker recovery, prefork cancellation, dead-parent uncertainty, changed PID-birth refusal, dirty-source refusal, immediate pidfd-registration failure after `Popen`, leader-exit descendants, STOP-confirmation timeout/SIGCONT, and failure-log errors. Negative plan/source/first-audit controls and explicit headroom admission are also covered.

One intermediate test run had a synthetic 150 ms registration timeout fire under host load in the unrelated source-change test. The ordinary tiny-process fixture now allows one second; tests intentionally checking registration timeout retain their explicit 150 ms bound. Production limits and proof gates did not change.

No existing file was edited. No Git operation was performed. Before any campaign: Root reviews this new source, the actual first shard is independently audited, the measured factors/concurrency/caps are chosen, the dedicated execution checkout and exact plans are frozen and privately pushed, and complete metadata admission passes. Source preparation alone authorizes no derivative campaign.
