## Evaluator and units

`repro_noise.py32–38,41–65,107–146` runs all448 fixed cells for1500steps, four comparisons in the recorded order `batch64,batch32,precision,bf16`; tail length500. For batch comparisons, the first448 rows of A/B have the same steering and temperature, and B has448 additional rows. Precision compares float64 A with float32 B at the same448 cells. This is deterministic expected-embedding feedback; argmax is a readout, not the state-update rule or a sampled token stream.

SoftLoop original68–117 builds a separate steered prefix cache for each layout, then returns copies of the final prefix token's embedding as the starting one-token window. Thus batch comparisons share the same initial embedding but the intervention also changes **prefix-cache rounding**, not just later kernels. Shallow copies share the model/SteeredModel; preparation replaces each loop's cache/row fields, while sequential logits calls install the calling loop's steering and reset it in `finally` (original119–148). I found no source-level simultaneous-state race in this sequential path. This is source reasoning, not runtime tensor-identity attestation.

For zero-based array rowi, `step` returns the updated state and the probabilities calculated from its input (SoftLoop150–155). Therefore `dist[i]` measures the post-step soft-window distance at human stepi+1; `agree[i]` compares the most-probable tokens of the corresponding **pre-update readouts**. With window1, the last-window slice is the whole dynamic soft state; it is not a distance between all network activations or prefix caches. Distance is asymmetric and dimensionless: `||x_A−x_B||₂/||x_A||₂`, using A in the denominator. Norm/difference arithmetic is cast to double, but the retained distance arrays are float32 (`repro_noise.py52,58–60`). Casting low-precision states to double does not restore their lost precision. Agreement arrays retain booleans only, not IDs, probabilities, logits or margins.

## Order-dependent bfloat16 implementation

The actual comparison order makes the following source-level behavior relevant specifically to REPRO1. Engine original193–194 calls `keep_float64_norms` for the first float64 model. That function original255–260 replaces RMSNorm **classes'** forward methods with input-dtype variance/rms arithmetic. The later bfloat16 model is created through the same class after this patch (`repro_noise.py126–142`), so its norms use that patched input-dtype path, unlike the usual float32-upcast RMSNorm path. This observation is not merely a dtype-label inference; it follows from the captured global class mutation and load order.

Separately, `make_loop` first constructs a float32 SoftLoop, whose `self.E` was captured in float32 at SoftLoop original49, and then casts `loop.model` to bfloat16 and changes `loop.dtype` (`repro_noise.py33–37`). It does not rebuild the existing E reference. The update still uses float32 probabilities/state and `p @ self.E` (original150–155), while the starting embedding is retrieved from the now-cast model. The result should be described as this exact bfloat16-model/mixed-state/readout implementation. Avoid promoting it to a universal claim about ordinary serving kernels or all bfloat16 configurations. The source contains the norm/rotary repair and stale-hook refusal for float64; that is an implementation premise, not an independent historical backend/asset validation.

Do **not** transfer this order effect to REPRO-T: its order is separately reported as bfloat16 before float64. No new model call is necessary to report the REPRO1 source scope.
